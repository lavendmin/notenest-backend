## 3. 요청 SQL 에 미디어 바이트 컬럼이 없다

로컬 프로파일의 `org.hibernate.SQL` DEBUG 로그에서 요청 스레드(`nio-8086-exec-*`) SQL 만 뽑아 셌다.

| 요청 | SQL 수 | `.image`·`.audio` 참조 |
|---|---|---|
| 목록 `GET /api/music/filter?…maxPrice=100000…` | 4 | **0** |
| 상세 `GET /api/music/{id}` | 3 | **0** |
| 내 곡 `GET /api/music/my-music?size=10` | 13 | **0** |

상세의 곡 조회는 엔티티 전체를 불러온다. 그 SELECT 에 들어간 컬럼은 스칼라 필드와 `cover_*`·`preview_*`·`full_demo_*` 키·메타데이터뿐이다. 전체 목록은 원시 출력에 있다.

## 4. DB 에 원본 바이트가 없다

| 확인 | 결과 |
|---|---|
| 스키마의 BLOB·BINARY 계열 컬럼 수 (`notenest` 전체) | **0** |
| `music` 논리 크기 (`information_schema.data_length`) | 0.16MiB (500행) |
| `music.ibd` 물리 파일 | LOB 삭제 직후 **1,774,190,592B** → 재구성 후 **294,912B** |
| 곡·키·입찰 | 500 / 커버 키 500 / 입찰 1,248 — 재구성 전후 동일 |

- **관찰:** MariaDB 10.11 의 `DROP COLUMN` 은 기본이 INSTANT(메타데이터만 변경)다. 그래서 컬럼을 지워도 LOB 페이지가 테이블스페이스에 남아 파일이 1.77GB 그대로였다.
  `OPTIMIZE TABLE`(InnoDB 에서는 재구성·분석)로 공간을 회수했고, 삭제한 바이트가 물리적으로도 사라지게 했다.
  이 단계를 `nb1-03` 의 STEP 5 와 리허설에 추가했다.
- 위 수치는 재시드 뒤의 시드 N=500 상태다. 삭제 전후의 DB 용량을 같은 조건으로 비교한 값이 아니므로 "DB 용량 N% 감소" 식으로 쓰지 않는다. 용량 비교는 재측정 문서에서 같은 시드 조건으로 따로 기록한다.

- 앱은 presigned URL 을 로그에 쓰지 않는다.
- 검증 스크립트가 만료 테스트용으로 로컬 임시 폴더에 저장한 URL 파일 2개(이미 만료)는 삭제했다.
- 레포에 커밋한 원시 출력은 서명·자격증명을 가린 상태다.
- 자격증명은 사용자 환경변수로만 주입했다. 코드와 설정 파일에는 값이 없다.

## 결론
LOB 삭제 후에도 기능 계약과 권한 규칙이 삭제 전과 같게 동작한다. DB 에는 미디어 바이트가 논리적으로도 물리적으로도 남아 있지 않다. 다음 단계는 NA1(N=500)·NA2(N=100) 재측정이다.
