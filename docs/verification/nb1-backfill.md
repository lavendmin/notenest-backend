# NB1 백필 실행 기록 — 저장 구조 전환 리허설

실행일: 2026-09-25 / 코드: `e58d5f3` / JVM: Java 17.0.12 / 버킷: `notenest-media` (ap-northeast-2)
대상: 로컬 DB의 NA1·NA2 성능 측정용 시드 N=500 (곡마다 오디오 더미 3MB·이미지 더미 300KB)

> **운영 이관이 아니다.** 실제 사용자·실제 음원은 0건이다. 이 실행은 LOB→객체 저장소 전환 절차를 실제 S3에서 리허설한 것이다.
> 리허설로 확인한 것은 결정적 키, 재실행 안전성, 존재·크기·해시 대조, 누락 0건이다. 별도 복구 시스템은 두지 않았다.
> 백필 시점에는 LOB 를 지우지 않았다. 전환 게이트 통과 후 nb1-03 으로 LOB 컬럼을 삭제했다.

## 실행

> 백필 코드(`MediaBackfillRunner`·`MediaBackfillService`, backfill 프로파일)는 LOB 컬럼 삭제 커밋에서 제거했다.
> `image`/`audio` 필드를 읽는 일회성 코드라 LOB 삭제 이후에는 둘 수 없기 때문이다. 아래 실행은 커밋 `e58d5f3` 기준이다.

```
./gradlew bootRun --args='--spring.profiles.active=local,backfill'
```

backfill 프로파일로 실행하면 웹 서버와 경매 스케줄러 없이 백필과 대조만 하고 끝난다. 누락·불일치가 있으면 비정상 종료한다.

- 재실행하면 이미 이전된 곡이 대상에서 빠진다. 새로 올린 객체가 없고 버킷 객체 수도 그대로다.
- 대조는 LOB의 SHA-256과 S3가 저장 시 기록한 SHA-256 체크섬을 곡마다 비교한다.

## 관찰

- 업로드 처리량은 약 1.5MB/s(곡당 약 2.2초)였다. 곡마다 트랜잭션 하나로 순차 처리하고, SHA-256 체크섬 업로드를 쓴 결과다. 병렬화는 리허설 범위 밖이라 하지 않았다.
- 재실행 소요 122초는 거의 전부 대조 시간이다. LOB 1.65GB를 읽어 해시를 계산하고 HEAD를 1,000번 호출한다.

## 다음

LOB 컬럼 삭제는 이 대조 결과(누락 0)를 전제로 한다. 삭제 전에 할 일은 두 가지다.
1. 읽기 fallback 코드를 제거한다.
2. 삭제 후 재측정용 시드 방식을 정한다. 기존 시드 스크립트는 LOB 컬럼에 더미를 넣기 때문이다.
