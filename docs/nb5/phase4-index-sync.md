# NB5 Phase 4 — 색인 갱신과 불일치 복구

작업일: 2026-09-26 / 기준 `f3ad8f9`(Phase 3)

## 0. 요약

- 곡을 바꾸는 모든 경로(등록·수정·삭제·입찰 현재가·좋아요·경매 마감)가 저장 뒤 **검색 문서 동기화를 요청**한다. 동기화 요청은 활성 트랜잭션이면 커밋 후, 없으면 저장 직후 실행된다.
- 동기화는 **전용 단일 쓰기 스레드**에서 돌고, 실행 시점의 커밋된 행을 다시 읽는다. 그래서 이벤트 순서가 바뀌거나 중복돼도 최신 상태가 남는다. 쓰기 요청은 색인을 기다리지 않는다(ES 장애 중에도 등록 응답 26~29 ms).
- 색인 오류는 3회 재시도한 뒤 기록만 한다. DB 성공을 되돌리거나 오류로 응답하지 않는다.
- 모든 문서에 **`source_hash`**(결정적 SHA-256)를 저장한다. **대조 작업**이 DB 와 색인을 ID·해시로 비교해 누락·불일치는 upsert 하고 잔존 문서는 삭제한다. 주기 실행은 10분 간격이다.
- 재현·복구: 누락(동기화 유실·쓰기 거부), 불일치(이벤트 없는 DB 변경), 잔존(이벤트 없는 삭제), 색인 전체 유실을 모두 대조 1회로 복구했다. **2차 대조의 변경 건수는 0**이다(fake 색인과 실제 ES 모두).
- **실측 발견 — 타임아웃은 실패가 아니다.** ES 를 멈춘 동안 타임아웃으로 "실패" 기록된 쓰기가, ES 가 되살아난 뒤 늦게 반영됐다. 그래서 실패 기록은 "미확인" 신호로 다루고, 수렴은 원본 기준 대조가 보장한다.
- 테스트: 기본 `./gradlew test` **220개 통과**(ES 없이), 실제 ES `./gradlew nb5IntegrationTest` **14개 통과**.

## 1. 동기화 계약

```
서비스 저장(커밋) ─▶ MusicSearchEvents.changed(id, reason)
                     └▶ @TransactionalEventListener(AFTER_COMMIT, fallbackExecution=true)
                          활성 트랜잭션: 커밋 후 / 롤백: 실행 안 함 / 트랜잭션 없음: 즉시
                          └▶ 단일 쓰기 스레드(큐 10,000) ─▶ DB 에서 id 행 재조회
                                 ├ 있음 → MusicSearchDocument.from(행) upsert (_id = music_id, 멱등)
                                 └ 없음 → 문서 삭제(없어도 오류 아님)
                             색인 오류 → 최대 3회(200ms·400ms 간격) → 그래도 실패면 SearchSyncRecorder 에 '미확인' 기록
대조(10분 주기, 같은 쓰기 스레드) ─▶ 색인 id→source_hash 전수 + DB 전수 재계산
                                     누락·불일치 upsert, 잔존 삭제 → refresh
```

| 설계 선택 | 이유 |
|---|---|
| 이벤트에 바뀐 값을 싣지 않고 id 만 보냄 | 실행 시점에 원본을 다시 읽으므로 순서 뒤바뀜·중복에 안전하다. 삭제도 같은 경로(행 없음 → 삭제) |
| `@TransactionalEventListener(fallbackExecution = true)` | 서비스마다 트랜잭션 경계가 다르다(등록·수정·삭제·입찰은 트랜잭션 없음, 좋아요는 메서드 트랜잭션, 경매 마감은 스케줄러 사이클 트랜잭션). 한 방식으로 "커밋된 것만 반영"을 보장한다. 계약은 테스트 3개로 고정했다 |
| 단일 쓰기 스레드, 대조·전체 재색인도 같은 스레드 | 색인 쓰기가 한 줄로 서므로 대조가 방금 동기화한 최신 문서를 옛 스냅샷으로 덮지 않는다. 대조 중 커밋된 변경은 뒤에 줄 선 동기화가 최신 행으로 다시 반영한다 |
| 비동기(요청 스레드는 기다리지 않음) | 경매 입찰·등록 응답이 검색 엔진 지연·장애에 묶이지 않는다. 대가로 eventual consistency 창이 생긴다(정상 시 약 1초) |
| 영속 큐(Outbox)·MQ 없음 | ACTION_PLAN 범위. 메모리 큐가 프로세스 중단으로 사라지면 다음 대조가 복구한다 |

설정([application.properties](../../src/main/resources/application.properties)): `notenest.search.sync.async=true`, `max-attempts=3`, `backoff-millis=200`, `notenest.search.reconcile.enabled=true`, `initial-delay=PT5M`, `fixed-delay=PT10M`. 스케줄링 전체(`notenest.scheduling.enabled`)가 꺼져 있으면 주기 대조도 돌지 않는다.

## 2. 변경 경로

| 경로 | 호출 위치 | 트랜잭션 경계 | 동기화 시점 | 바뀌는 문서 필드 |
|---|---|---|---|---|
| 곡 등록 | `MusicServiceImpl.createMusic` save 뒤 | 없음(save 자체 커밋) | 즉시 | 전체 |
| 곡 수정 | `updateMusic` save 뒤 | 없음 | 즉시 | 제목·부제·장르·설명·태그·BPM·키·커버 키 |
| 곡 삭제 | `deleteMusic` delete 뒤 | 없음 | 즉시 | 문서 삭제 |
| 입찰 | `BidServiceImpl.createBid` bid save 뒤 | 없음. 곡 현재가는 OSIV 로 bid 커밋 때 함께 flush | 즉시 | 현재가·가격 필터 값 |
| 좋아요·취소 | `LikeMusicService.toggleLikeMusic` | `@Transactional` | 커밋 후 | 좋아요 수 |
| 경매 마감 | `processAuctionEnd`(`checkAuctionEnd` 사이클) | 사이클 전체 단일 트랜잭션 | 사이클 커밋 후 | status 0→1(검색 제외) |

동기화하지 않는 경로와 이유:
- 입찰 삭제(`deleteBid`): 곡 행을 바꾸지 않는다. 현재가를 다시 계산하지 않는 기존 결함(Phase 0)은 NB5 범위 밖이고, 색인은 DB 를 그대로 따른다.
- 경매 무산 메일 플래그·결제 후속: 검색 문서 필드가 아니다.
- 판매자 닉네임: 변경 API 가 없다. 생기면 fan-out 대신 대조가 복구한다(P0 한계).

| **쓰기 거부**(색인 write block — 디스크 flood-stage 때 ES 가 거는 것과 같은 차단) | 등록 201(26 ms) → 3회 `cluster_block_exception` → 기록 → 검색에 **없음(확정 누락)** → 차단 해제 후 대조 #1 누락 1 → #2 변경 0 |
| **응답 없음**(ES 컨테이너 일시정지) | 등록 201(29 ms) → 3회 응답 타임아웃(3s), 9.8초 뒤 기록 → 재개 후 **요청이 늦게 반영됨**(true) → 대조 #1·#2 모두 변경 0 |

두 번째 시나리오의 교훈: 클라이언트 타임아웃은 "실패"가 아니라 "결과 미확인"이다. 요청이 이미 서버에 전달됐다면 서버가 되살아난 뒤 처리한다. 그래서 `SearchSyncRecorder` 는 이를 "미확인"으로 기록하고, 정확성은 원본 기준 대조에 맡긴다. 테스트도 늦게 반영된 경우와 누락된 경우를 모두 허용하되, 대조 뒤에는 항상 원본과 같고 2차 대조는 0 이어야 한다고 단언한다.

Phase 3 의 검색 IT 11개(품질 재현·API 계약)도 매핑에 `source_hash` 를 더한 뒤 그대로 통과했다.

## 4. 한계 (P1 후보·Phase 5)

- **eventual consistency 창:** 정상 시 반영까지 약 1초(기본 refresh 주기). 동기화가 실패하면 최대 다음 대조까지(기동 후 5분, 이후 10분 간격) 검색이 DB 와 다를 수 있다.
- **메모리 큐:** 커밋 후 프로세스가 중단되면 큐에 있던 동기화를 잃는다. 대조가 복구한다(영속 큐 없음 — 의도한 범위).
- **늦게 도착한 옛 쓰기:** 타임아웃된 요청이 나중에 반영되면서, 그 사이 성공한 더 새 쓰기를 덮을 수 있다. 다음 대조의 해시 비교로 고쳐지지만 그때까지 옛 값이 보일 수 있다. 외부 버전(`version_type=external`)으로 막는 것은 P1 후보다.
- **대조 규모:** DB·색인 전체를 메모리에 올려 비교한다(1만 곡 규모 기준). 대규모 카탈로그는 구간별 대조가 필요하다.
- **전체 재색인:** 고정 이름 색인을 지우고 다시 만들어 그동안 503 이다. 운영 복구에는 무중단인 대조를 쓴다. alias 교체는 P1.
- LIKE + 규칙 자동 폴백 P1, 판매자 닉네임 fan-out 없음, ES 최고 메모리·API p50/p90 은 Phase 5.
- CHECK 제약 적용은 **미해결 유지**(Phase 1 §6).
