# ADR-001 NB5 상품 검색 엔진 선택

- 상태: **제안 — 소민님 승인 대기** (Phase 2 중단점)
- 날짜: 2026-09-26
- 근거: [phase2-spike-comparison.md](phase2-spike-comparison.md), qrels v1(승인·고정, 해시 `839dadd6…`)

## 맥락

현재 `GET /api/music/filter?searchTerm=` 은 다섯 필드를 `%keyword%` 로 OR 조회한다. 결과 순서는 관련도가 아니라 등록 순서로 정해진다. Phase 1 기준선은 nDCG@5 0.5084, 곡명 탐색 MRR@5 0.3889 이다. 10,000곡에서는 T1 MRR@5 가 0.3611 로 떨어진다(`love` 358위).

같은 25개 질의, 같은 qrels v1, 같은 사전 고정 설정(필드 가중치·정확 일치·한글 장르 별칭, 커밋 `03546be`)으로 후보를 비교했다.

## 결과 요약 (평가 코퍼스 57곡, k = 5)

| 후보 | 전체 nDCG@5 | T1 MRR@5 | T3 분위기 | 10,000곡 T1 MRR@5 | 서버 측 검색 시간 10,000곡 p50/p90 | 추가 인프라 |
|---|---|---|---|---|---|---|
| 현재 LIKE | 0.5084 | 0.3889 | 0.5079 | 0.3611 | 20.2 / 30.0 ms | 없음 |
| LIKE + 같은 질의 규칙 (사후 대조군) | 0.8359 | 1.0000 | 0.7753 | 1.0000 | 35.1 / 46.6 ms | 없음 |
| MariaDB FULLTEXT (min_token_size=1) | 0.8472 | 0.9444 | 0.8228 | 0.9444 | 25.4 / 35.3 ms | 서버 설정 변경·재시작, FT 인덱스 6개 |
| **Elasticsearch 8.11.1 + Nori** | **0.8860** | **1.0000** | **0.8757** | **1.0000** | took 3 / 5 ms (왕복 10.7 / 14.1 ms) | 컨테이너 1개(이미지 748MB, 메모리 상한 1GB 도달) |

질의별 승·무·패는 이렇다. ES 는 현재 LIKE 대비 19승 6무 0패, LIKE + 규칙 대비 8승 17무 0패, FULLTEXT min 1 대비 7승 16무 2패다.

## 결정 (제안)

**Elasticsearch 8.11.1 + Nori 를 `searchTerm` 경로의 P0 구현으로 채택한다.** 정확 일치 우선·한글 장르 별칭 같은 질의 규칙은 엔진과 무관하므로 ES 질의 안에 그대로 옮긴다. 비검색 경로(QueryDSL)는 바꾸지 않는다.

근거:
1. ACTION_PLAN 의 기준("고정 평가셋에서 관련도 요구를 충족하지 못하면 ES 를 P0 구현안으로 선택")에 해당한다. 현재 LIKE 는 T1 MRR@5 0.39 로 곡명 탐색 요구를 충족하지 못한다.
2. 같은 규칙을 넣은 MariaDB 대안보다 품질이 높고 **질의 단위 퇴행이 없다**(LIKE + 규칙 대비 0패). 이득은 한국어 처리가 필요한 질의에 몰려 있다. 띄어쓰기(Q03 `여름 밤` 0.87→0.97), 조사(Q01·Q02), 어순·다단어(Q20 `잔잔한 피아노` 0.78→0.92, Q21 `신나는 댄스` 0.66→0.92, Q24 `피아노 발라드` 0.62→0.82)다.
3. 검색 시간은 판단 근거가 아니지만 불리하지도 않다(엔진 측 took p90 5 ms). API 수준 비교는 Phase 5 에서 같은 부하 조건으로 한다.

## 기각한 대안

| 대안 | 기각 이유 | 다시 볼 조건 |
|---|---|---|
| 현재 LIKE 유지 | T1 MRR@5 0.39, 데이터가 늘수록 정확 제목이 밀려남(10,000곡 `love` 358위) | — |
| **LIKE + 질의 규칙** (인프라 추가 없음) | 가장 강력한 대안이다. 전체 nDCG 0.84 로 ES 와 0.05 차이이고 운영 비용이 없다. 다만 ① 부분 문자열이 연속해야 해서 다단어·어순이 다른 질의가 약하다(Q21 0.66, Q24 0.62). ② 필드 적중 여부만 세고 용어 가중치(IDF)가 없어, 데이터가 늘면 같은 점수의 곡이 등록 순서로 정렬된다. ③ 10,000곡에서 서버 측 시간이 가장 길다(p90 46.6 ms, 필드마다 LIKE 6개 + 풀스캔) | ES 운영 비용(메모리·동기화)을 감당할 수 없게 되면 이 안으로 후퇴한다. **ES 장애 시 폴백 경로 후보**로도 남긴다(Phase 3·4 에서 결정) |
| MariaDB FULLTEXT (min_token_size=1) | 품질은 LIKE + 규칙과 비슷하다(6승 14무 5패). ① 형태소 분석이 없어 조사·복합어를 못 다루고(Q08 `너의 이름` 0.69), MariaDB 에는 ngram 파서도 없다(`Function 'ngram' is not defined`). ② 한글 2글자 토큰을 쓰려면 **서버 전역 설정 변경과 재시작, FT 인덱스 재구성**이 필요하다. 기본값(min 3)이면 `이별`·`비트`·`너의 이름`이 0건이고 전체 0.7059 다. ③ 인덱스 변경이 테이블 재구성 ALTER 인데, 이 로컬 환경에서는 재구성 ALTER 실패 이력이 있다(Phase 1 §6). ④ 이 스파이크의 질의 형태에서는 LIKE 보다 빠르지 않았다 | 한국어 형태소가 필요 없는 영문 위주 카탈로그라면 재검토 |

## 결과와 비용 (ES 채택 시 받아들이는 것)

- **운영:** 컨테이너 1개가 추가된다. 측정 중 메모리 사용량이 1017 MiB 로 상한(1 GiB)에 닿았다(힙은 231/512 MB 사용, OOM 없음). Phase 3 에서 상한을 1.5 GiB 로 올릴지 정한다. 로컬 설정은 보안을 끈 단일 노드이며 운영 권장 설정이 아니다.
- **일관성:** MariaDB 가 원본이고 ES 는 read model 이다. 등록·수정(BPM·키 포함)·삭제·현재가·좋아요·경매 상태 변경 후 색인 갱신이 필요하다. eventual consistency 창과 누락·불일치 복구(sourceHash 대조)가 Phase 4 의 일이다.
- **장애:** ES 장애 시 검색 경로를 어떻게 할지(오류 응답 또는 LIKE + 규칙 폴백) 정해야 한다.
- **범위:** T2 의 텍스트 조건(`BPM 90`, `120`, `Am`)은 어떤 엔진으로도 0.64 이하다. 이는 엔진이 아니라 질의 해석 문제이고, 구조화 필터(`bpmMin`·`musicalKey`)로 해결하는 것이 계약이다. P0 에서 자연어 조건 파싱은 하지 않는다.

## 해석상 주의 (포트폴리오 서술 기준)

- 개선분의 **대부분은 질의 규칙**(정확 일치 우선, 한글 장르 별칭, 설명 포함)에서 나왔다. 전체 nDCG 0.51 → 0.84 가 규칙 몫이고, 엔진(Nori)의 추가 몫은 0.84 → 0.89 다. "Elasticsearch 로 nDCG 0.51→0.89" 라고만 쓰지 않는다.
- 평가셋은 25개 질의 × 57곡의 **검증용 가설**이다. 실제 사용자 검색 로그가 아니고 표본이 작다. 0.05 차이는 질의 8개의 개선에서 나온 값이다.
- LIKE + 규칙 대조군은 FULLTEXT 기본 설정 결과를 본 뒤 추가했다(가중치는 사전 고정값 그대로). 성능 수치는 엔진 측 시간이다. MariaDB 는 `SHOW PROFILES`, ES 는 `took` 과 클라이언트 왕복이라 정의가 다르다. API p50/p90 비교는 Phase 5 에서 한다.
