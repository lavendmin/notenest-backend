# NB5 병합 전 리뷰 반영 (2026-09-26)

리뷰 결론: "NB5 구현·실험은 완료됐지만 아직 merge-ready 는 아니다." 병합 차단 항목 2개와 보조 지적 2개를 아래와 같이 반영했다.

## 1. [P1 차단] 새 Elasticsearch 부트스트랩이 안전하지 않음 → 해결

지적: ES 데이터 볼륨이 없고 기동 재색인은 기본 false 이며 첫 대조는 기동 5분 후다. 그래서 ES 를 새로 띄우면 최대 5분간 검색이 503 이거나 비어 있다. 그 사이 곡 변경이 들어오면 단건 upsert 가 ES 자동 색인 생성을 일으켜 Nori·strict 매핑 없는 기본 매핑 색인이 생길 수 있다.

| 권장 | 반영 |
|---|---|
| 기동 시 항상 대조를 같은 쓰기 큐에 먼저 등록 | [SearchIndexBootstrap](../../src/main/java/com/notenest/search/SearchIndexBootstrap.java) — `SmartInitializingSingleton`(모든 빈 생성 직후, 웹 서버가 요청을 받기 전)에서 쓰기 큐 **첫 작업**으로 대조를 넣는다. `reindex-on-startup=true` 면 전체 재색인. 기존 `SearchIndexStartupRunner` 는 대체돼 삭제했다 |
| ES 가 꺼져 있어도 앱 기동은 실패하지 않게 경고만 | 쓰기 스레드에서 비동기로 돌고, 실패하면 `[SEARCH-BOOTSTRAP] … failed` WARN 과 상태 `FAILED` 만 남긴다. `SearchUnavailableContractTest` 가 닫힌 포트로 기동해 FAILED·목록 200·검색 503 을 확인한다 |
| 단건 upsert 전에도 올바른 매핑의 색인 보장 | `ElasticsearchMusicSearchIndex.upsert/upsertAll` 이 쓰기 전에 `ensureExists()`(없으면 매핑 파일로 생성, 동시 생성은 성공으로 처리)를 한다. 삭제는 색인이 없으면 할 일이 없다. 추가로 compose·통합 테스트 ES 에 `action.auto_create_index=false` 를 넣어 기본 매핑 자동 생성을 원천 차단했다(이중 방어) |
| "기존 DB + 빈 ES" 통합 테스트 | [MusicSearchBootstrapIT](../../src/test/java/com/notenest/search/it/MusicSearchBootstrapIT.java) — 앱을 **실제로 두 번 기동**한다. 1차에서 DB 에 곡 저장 → 종료 → 색인 삭제(새 ES 상태) → 2차 기동. 곡 변경 없이 부트스트랩 대조만으로 `missing=2` 를 채워 검색되고, 매핑은 `dynamic: strict`·`title` analyzer `ko` 다. 이어서 색인을 지운 상태에서 단건 동기화가 먼저 와도 올바른 매핑으로 다시 만든다. 자동 생성 금지도 확인한다(없는 색인에 쓰기 → `index_not_found`) |

부수 수정: 부트스트랩이 기동 때 쓰기 큐에서 돌면서 `MusicSearchApiIT` 가 테스트 스레드에서 직접 호출하던 전체 재색인과 경합했다(`resource_already_exists_exception`). "모든 색인 쓰기는 단일 쓰기 스레드" 규칙대로 테스트도 `synchronizer.submit(...)` 로 재색인하게 고쳤다. 통합 테스트 전체를 두 번 연속 실행해 16/16 통과했다.

## 2. [P1 차단] BPM·키 CHECK 제약이 실제 스키마에 적용되지 않음 → P1 로 분리

선택: **CHECK 를 P1 로 분리하고 P0 완료 조건을 애플리케이션 검증으로 한정한다.** 환경을 고치는 선택지는 기존 `notenest-db` 컨테이너의 데이터 디렉터리 구성을 바꿔야 해서 "기존 컨테이너 삭제·초기화 금지" 조건과 부딪힌다. 또 "CHECK 는 main 에 반영하지 않고 미해결로 유지"한다는 기존 결정과도 맞지 않는다.

- [nb5-01](../../scripts/migration/nb5-01-add-bpm-musical-key.sql) 은 이제 **컬럼 추가만** 한다(instant ALTER, 테이블 재구성 없음). 리허설([raw](raw/review-nb5-01-rehearsal.txt))에서 추가·멱등·기존 행 보존·롤백을 확인했다. 실제 측정 스키마 `notenest_nb5` 에는 두 번 적용해 오류 없이 통과했다([raw](raw/review-nb5-01-apply-notenest_nb5.txt)).
- CHECK SQL·실패 기록·착수 조건은 실행 스크립트가 아닌 설계 문서 [p1-db-check-constraints.md](p1-db-check-constraints.md) 로 옮겼다. P0 에서 범위·형식은 애플리케이션이 집행한다(등록·수정·필터 400, 테스트로 고정).

## 4. [보조] 프론트가 항상 `sortBy=latest` 를 보냄

- 백엔드 범위상 병합 차단은 아니다. 관련도순 개선은 `sortBy` 를 **생략한** API 호출로 시연한다. 예: `GET /api/music/filter?searchTerm=봄비`. 원 프론트(`bidder-front/src/pages/Songs.js`)는 정렬 기본값이 `latest` 이고 선택지에 관련도가 없다. 화면에 반영하려면 검색어가 있을 때 `sortBy` 를 빼거나 `relevance` 선택지를 추가하는 소폭 수정이 필요하다(NB5 범위 밖).

## 6. 작업 중 사고 — 로컬 `notenest` DB 에 테스트 데이터가 들어감 (2차 리뷰에서 정리 완료)

`MusicSearchBootstrapIT` 첫 버전은 설정을 `SpringApplicationBuilder.properties()` 로 넘겼다. 이 값은 "기본값"(최하위 우선순위)이라 `application-local.properties` 의 datasource(로컬 `notenest` DB)에 덮였다. 그 결과 1차 실행 때 **`notenest` DB 에 사용자 1행(`seller@test.local` / 윤슬)과 곡 2행(봄비·여름밤, 2026-09-26 17:21:39)이 들어갔다**(곡 100 → 102, 사용자 12 → 13). 로컬 `notenest-es` 는 꺼져 있어 색인에는 아무것도 쓰이지 않았다.

- 재발 방지: 설정을 커맨드라인 인자(`--key=value`, 최우선)로 넘기고, 기동 직후 실제 datasource 가 전용 DB(`notenest_es_boot_it`)가 아니면 아무것도 쓰기 전에 멈추는 가드를 넣었다. 수정 후 두 번 실행해 `notenest` 가 더 바뀌지 않음을 확인했다.
- 같은 조사에서 드러난 기존 문제: `NoteNestApplicationTests`(기존 스모크 테스트)는 datasource 를 지정하지 않아 `./gradlew test` 때마다 로컬 `notenest` DB 에 `ddl-auto=update` 로 붙는다. 그래서 Phase 1 에서 엔티티에 `bpm`·`musical_key` 를 추가한 뒤의 테스트 실행이 **`notenest.music` 에 두 컬럼을 추가한 것으로 보인다**(테이블 `CREATE_TIME` 2026-09-26 14:32 KST). NB5 에서는 이 테스트에 `notenest.search.bootstrap.enabled=false` 만 추가했다(로컬 ES 에 색인을 만들지 않도록). DB 연결 방식 자체는 기존 동작이라 바꾸지 않았다.
- 정리: 2차 리뷰 결정대로 처리했다(§7).
