**채택 근거는 성능이 아니다.** ADR-001 대로 근거는 LIKE + 질의 규칙 대비 조사·띄어쓰기·어순이 다른 한국어 검색에서 확인한 8승 17무 0패, T3 0.7753 → 0.8757 이다. 개선의 대부분은 엔진과 무관한 질의 규칙(정확 일치 우선·한글 장르 매핑·상세 설명 포함)에서 나왔다. 응답 시간 개선은 같은 조건에서 측정된 보조 결과다. 평가셋은 도메인 인터뷰를 반영한 **검증용 가설**이며 실제 사용자 검색·구매 성과가 아니다.

## 3. 성능 결과와 해석

| 지표(검색, 웜 3회 평균) | 기준선 LIKE | 최종 ES | 차이 |
|---|---|---|---|
| p50 | 35.30 ms | 9.67 ms | 3.65배 |
| p90 | 42.68 ms | 12.93 ms | 3.30배 |
| p95 | 45.47 ms | 13.88 ms | 3.28배 |
| 처리량(대기 0.1s) | 74.8~75.4 req/s | 90.4~90.9 req/s | 스크립트 상한에 가까움 — 비교하지 않음 |
| 포화 처리량(대기 0) | 150.8 req/s (p90 85.37 ms) | 877.6 req/s (p90 14.57 ms) | 5.82배 |

해석과 경계:
- **왜 빠른가:** 기준선은 검색마다 SQL 2개(본문 + count)를 보낸다. 각각 진행 중 8,036행 풀스캔 + filesort + 행마다 LIKE 5개(Phase 0 EXPLAIN)다. 최종은 역색인 검색 1회로 `_source` 에서 목록 DTO 를 만든다(비로그인이라 좋아요 조회 없음). 이것은 이 규모·이 질의 분포에서의 결과이며 운영 용량 주장이 아니다.
- **측정 안정성:** 무검색 목록은 두 앱이 같은 경로(QueryDSL)를 쓴다. p50 이 17.24~17.48 ms 로 같아 두 측정 사이 환경이 흔들리지 않았음을 보여 준다. 동시에 비검색 경로의 퇴행이 없다는 근거다.
- **Phase 0 수치와 다른 이유:** Phase 0 기준선(p50 51.0 / p90 67.6 ms, 무검색 37.3 ms)은 SQL 콘솔 로그를 켠 상태였다. 이번에는 두 앱 모두 로그를 끄고 같은 조건으로 다시 쟀다. 비교는 이 문서의 두 측정끼리만 한다.
- **한계:** 단일 PC, 앱·DB·ES·k6 가 한 기계, 1회 교대(ES → 기준선) 측정. 곡 수 1만, 질의 25개 균등 분포는 실제 트래픽 분포가 아니다.

## 4. 자원·운영 비용

### 4.1 Elasticsearch 메모리 (승인 결정 3 — 재색인·부하 중 최고치)

[raw](raw/phase5-es-memory.csv) — `docker stats`(컨테이너, 페이지 캐시 일부 포함)와 `_nodes/stats/jvm`, 1~2초 간격 295샘플.

| 구간 | 컨테이너 최고 | 힙 최고 |
|---|---|---|
| 기동 직후·57곡(측정 전) | 1,138.7 MiB | 343.9 MiB |
| 10,000곡 재색인 + 대조 | 1,234.9 MiB | 337.8 MiB |
| 검색 부하(warm1~3, 포화) | 1,261.6 MiB | **394.9 MiB** |
| 무검색 부하(ES 미사용) | 1,257.5 MiB | 314.0 MiB |
| 기준선 앱 측정 중(ES 유휴) | **1,273.9 MiB** | 342.0 MiB |
| **전체 최고** | **1,273.9 MiB (상한의 82.9%)** | **394.9 MiB (512 의 77%)** |

- OOM·재시작은 없었다. 컨테이너 최고치는 부하 때가 아니라 유휴 중에 서서히 늘어 나왔다. 페이지 캐시·오프힙 증가로 보이며 부하와 비례하지 않았다.
- 1GiB 상한 때(Phase 2)는 1,017 MiB 로 상한에 붙어 동작했다(OOM 없음). 1.5GiB 에서는 유휴 상태만으로 1,090 MiB 까지 올라간다. 즉 1GiB 에서는 커널이 캐시를 회수하며 상한에 눌려 있던 것으로 보인다. 이 수치는 컨테이너 메모리 표시값이며 필요 메모리 하한이 아니다. 1.5GiB 에서 여유는 약 260 MiB 로 크지 않으므로, 곡 수가 크게 늘면 다시 측정해야 한다.

## 5. 한계 (전체 정리)

| 한계 | 영향 | 대응 |
|---|---|---|
| 평가셋은 도메인 인터뷰 기반 검증용 가설(25질의·57곡) | 실제 사용자 검색 품질·구매 전환을 뜻하지 않는다 | 실제 로그가 생기면 qrels-v2 |
| eventual consistency | 정상 약 1초, 동기화 실패 시 다음 대조까지(첫 5분, 이후 10분) 검색이 DB 와 다를 수 있다 | 대조 주기 조정 |
| 메모리 큐 | 커밋 후 프로세스 중단 시 동기화 유실 | 대조가 복구(Outbox 는 범위 밖) |
| 타임아웃 후 늦은 반영 | 옛 값이 더 새 값을 덮을 수 있다(다음 대조까지) | 외부 버전(`version_type=external`) — P1 |
| 판매자 닉네임 fan-out | 변경 API 가 없다. 생기면 즉시 반영하지 않는다 | 대조가 복구 |
| 전체 재색인 중 503 | 고정 이름 색인 재생성 | 새 색인 → 검증 → alias 교체 — P1 |
| ES 장애 시 검색 불가 | 503 (결정 4) | LIKE + 규칙 자동 폴백 — P1 (결정 6) |
| 원 프론트엔드가 `sortBy=latest` 를 항상 보냄 | 화면에서는 관련도순이 적용되지 않는다 | 프론트 수정은 범위 밖 |
| 깊은 페이지 | 검색 결과 10,000번째 이후 400 | search_after 는 범위 밖 |
| 대조가 전수를 메모리에 올림 | 1만 곡 기준 0.63 s. 대규모는 구간별 대조 필요 | — |
| T2 텍스트 조건 | 0.64 이하 | 구조화 필터가 계약 |
| **DB CHECK 제약** | 로컬 바인드 마운트에서 적용 실패(errno 194), 원인 미분리 | **리뷰 반영: P1 로 분리**([p1-db-check-constraints.md](p1-db-check-constraints.md)). P0 는 애플리케이션 검증. nb5-01 은 컬럼 추가만 |
| 환경 | ES 클라이언트 8.10.4(서버 8.11.1), Testcontainers 1.21.4 로 테스트 전용 상향, Ryuk 비활성(이미지 수신 불가) | Phase 3·4 문서 참고 |

## 8. 서술 후보 (확정 전 — project-notes 반영은 논의 후)

ACTION_PLAN 의 이력서 한 줄 틀에 실측값을 넣은 **초안**이다. 수치 귀속을 지킨다.

> 검색 계약과 평가셋(25질의 qrels)을 구현 전에 고정하고 LIKE·FULLTEXT·Elasticsearch+Nori 를 같은 기준으로 비교해, 정확 일치·장르 매핑 규칙과 Nori 형태소 분석으로 nDCG@5 0.51→0.89(규칙 0.84, 형태소 +0.05)를 확인하고, DB·검색 인덱스의 누락·불일치를 source_hash 멱등 대조로 복구(2차 대조 0건)

- 성능(검색 p90 42.7 → 12.9 ms, 로컬 1만 곡)은 보조 수치다. 채택 근거가 아니므로 본문 앞에 두지 않는다.
- "검증용 가설 평가셋"이라는 성격과 규칙·엔진 귀속을 함께 쓴다. "Elasticsearch 로 0.51→0.89" 라고만 쓰지 않는다.
