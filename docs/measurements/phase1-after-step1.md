# Phase 1 — after 측정 (1차 개선: 스케줄러 쿼리화 + DTO 프로젝션)

측정일: 2026-07-19 (before와 동일 환경·동일 시드 스크립트 — [phase1-before.md](phase1-before.md) 참고)

## 적용한 개선 (세션 2)

1. **스케줄러 종료 대상 조회 쿼리화**: `musicRepository.findAll()`(전체 곡을 Lob 포함으로 로딩 후 자바 필터링)
   → `findEndedMusicUuids(now)` — 마감 지난 곡의 **UUID만** 조회. `auction_end_time` 인덱스 추가.
2. **목록 API DTO 프로젝션**: 최신순 목록이 엔티티(Lob 포함) 대신 필요한 컬럼만 `new MusicDTO(...)`로 조회.
   audio/image가 SELECT 절과 응답 JSON에서 제외됨.
3. 필터/마이페이지 목록(동적 Specification 경로)은 세션 3의 MusicAsset 테이블 분리가 구조적으로 해결 예정
   — "즉효 조치는 주 경로에, 근본 해결은 모델 분리로"의 단계적 적용.

## 1. 스케줄러 before → after

### N=100 (종료 대상 50곡)

| 항목 | before | after | 변화 |
|---|---|---|---|
| 종료 대상 파악 (조회 단계) | findAll 5~8초, 힙 +1.3~2.2GB | **0.07초, 힙 +4MB** | **~100배** |
| 웜 사이클 시간 (5회 평균) | 9.9초 (10초 주기 포화) | **4.9초** (5.5/5.4/5.1/4.4/4.6) | 2배 |
| 사이클 중 힙 피크 | 2.3GB | ~1.0GB | 절반 |
| 사이클당 SQL | 85개 | **135개 (증가!)** | 아래 참고 |

**쿼리 수가 늘어난 이유 (정직한 기록)**: before는 findAll이 전곡을 영속성 컨텍스트에 올려놔
낙찰 재방문의 `findById`가 1차 캐시에 히트했지만, after는 개별 조회가 실제 SQL로 나간다(+50개).
그런데도 사이클 시간이 절반이 된 것은 **병목이 쿼리 횟수가 아니라 Lob 데이터 전송량이었다는 증거.**
(재방문 자체의 제거는 Phase 3-C 구조 정리에서)

### N=500 (before에서 OOM으로 죽던 조건)

| 항목 | before | after |
|---|---|---|
| 사이클 완주 | **0회 — OutOfMemoryError** | **완주 (OOM 해소)** |
| 첫 사이클 (밀린 낙찰 250건 + 동기 메일) | — | 92초 |
| 이후 사이클 | — | 43~56초 |

**남은 문제 (세션 3의 근거)**: OOM은 사라졌지만 사이클 43~56초로 여전히 10초 주기 초과.
원인은 낙찰 재방문(`processAuctionEnd`)이 곡 **엔티티를 Lob 포함으로** 개별 로딩하기 때문
(250곡 × 3.3MB). 조회 경로 개선(1차)만으로는 한계 — **바이너리를 별도 테이블로 분리(2차)해야
어떤 코드 경로든 Lob을 끌고 오지 않는다.**

### 인덱스 사용 증빙 (EXPLAIN)

```
EXPLAIN SELECT music_uuid FROM music WHERE auction_end_time IS NOT NULL AND auction_end_time < NOW();
→ type: range
  key: idx_music_auction_end_time
  rows: 50
  Extra: Using where; Using index   ← 커버링 인덱스 (테이블 본체·Lob 페이지를 전혀 읽지 않음)
```

## 2. 목록 API before → after

before 공식값은 본인 실측 (2026-07-19): p(90) 9.18s / 처리량 1.25 req/s / 30초간 수신 4.1GB(요청당 ~91MB) / 요청당 쿼리 24개

after 공식값도 본인 직접 실측 (2026-07-19, 동일 스크립트 2회 중 웜 2회차 채택. 1회차: p(90) 179ms/47.7 req/s):

| 항목 | before (실측) | after (실측) | 변화 |
|---|---|---|---|
| p(90) | 9.18s | **81.5ms** | **약 113배** |
| avg / med | 7.1s / 7.24s | 53.8ms / 50.2ms | 〃 |
| 처리량 | 1.25 req/s (30초에 44회) | **64.4 req/s** (30초에 1,948회) | 약 52배 |
| 30초 총 수신량 | 4.1GB | **10MB** | 410분의 1 |
| 요청 1건당 응답 크기 | ~91MB | **~5.3KB** | 바이너리가 응답에서 제거된 직접 증거 |

주: 요청당 쿼리 수(24개)는 이 단계에서 변하지 않음 — N+1(좋아요 카운트) 제거는 세션 3.
쿼리 수가 그대로인데 91MB→5.3KB만으로 100배가 빨라졌다는 것 자체가 "병목은 쿼리 횟수가 아니라
Lob 전송량"이라는 스케줄러 쪽 결론과 일치한다.
