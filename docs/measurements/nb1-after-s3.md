시드: `scripts/seed/seed-music-s3.sql` — 곡·입찰 구조는 이전 시드와 같다(N=500: 곡 500·마감 250·입찰 1,248).

> **비교 기준:** [Java 17 기준선](nb1-baseline-j17-before-s3.md) (`83353d2`, LOB 저장, 2026-09-25 14:17~14:25).

> 기준선 문서에서 같은 구조의 세션 간 편차를 **약 2배**까지 관측했다(Java 21 오전 51.3s vs Java 17 오후 25.0s, 원인 미분리).
> 그래서 이 문서에서 시간 지표는 **2배를 크게 넘는 차이만** 개선으로 주장한다. 구조 지표(대상 수·SQL 수·힙·응답 크기·불변식)는 그대로 비교한다.
> 무필터 1차 진단(91MB→5.3KB)·N1·N2 수치와 섞지 않는다.

## NA1 — 경매 배치 사이클 (N=500)

조건은 기준선과 같다: 재시드 직후 앱 기동(스케줄러 켬), catch-up 마감과 결제 후속 잡 웜 사이클의 `[BATCH]` 로그 수집.
SQL 수는 직전 `[BATCH]` 줄 이후의 `Hibernate:` 문장 수다(측정 중 HTTP 요청 0건).

| 항목 | 기준선 (LOB, Java 17) | **S3 이후** | 변화 |

| 웜 결제 회차별 | 26,019·24,856·24,536·24,893·24,449ms | 1,323·1,250·1,170·1,327·1,305ms (6회차 1,496ms) | 회차 편차 ±10% 이내 |

### 불변식 (기준선과 동일)

| 대상 | 기준선 | S3 이후 |
|---|---|---|
| `bid.status` | PENDING 167 / FAILED 333 / NULL 748 | PENDING 167 / FAILED 333 / NULL 748 |
| `music.status` | 0=250 / 1=250 | 0=250 / 1=250 |
| 낙찰 메일 `bidder_email_sent` | 167 | 167 |
| 무산 메일 `auction_failure_email_sent` | 83 | 83 |

### 해석
- **남아 있던 병목이 사라졌다.** 기준선의 웜 결제 후속 잡은 결제 대기 곡 167곡마다 `findById(Music)`를 호출했다. 이때 음원 3MB·이미지 300KB LOB 까지 매 사이클 함께 읽었다.
  이제 곡 행에는 키·메타데이터만 있어서, **같은 SQL 502개**가 1.3초 안에 끝나고 10초 주기 안에 들어온다.
  SQL 수가 같다는 것은 조회 경로나 횟수를 바꾼 것이 아니라, **한 행이 싣는 데이터**가 줄어서 빨라졌다는 뜻이다.
- **힙:** 웜 사이클 힙이 GB 단위에서 수십~수백 MB 로 내려갔다. LOB 를 엔티티로 올리지 않기 때문이다.

### 관찰 — catch-up 구간의 `UPDATE music` 수 (원인 미분리)
catch-up 구간의 SQL 을 종류별로 비교했다([원시](raw/nb1-na1-catchup-sql-histogram.txt)).
- 조회 SQL(곡 SELECT 250, 입찰 SELECT 250)은 같다.
- `UPDATE music` 은 234 → 331, `UPDATE bid` 는 500 → 498 로 달랐다.
- 최종 상태(위 불변식)는 같다. 그래서 동작이 바뀐 것이 아니라, 같은 변경을 DB 에 반영(flush)하는 횟수가 달라진 것으로 본다.
- 가능한 요인이 두 가지 있다.
  - 사이클 전체가 한 트랜잭션이다(N2 문서의 한계: 자기 호출이라 곡별 REQUIRES_NEW 가 무효). 그래서 자동 flush 시점에 따라 한 곡의 UPDATE 가 나뉘거나 다음 사이클로 넘어갈 수 있다. 실제로 기준선은 첫 결제 사이클이 522(이후 502)로 20개 많았다.
  - 기동 직후 두 잡의 실행 순서가 달랐다. 기준선은 결제 후속(대상 0)이 먼저, 이번에는 마감이 먼저 돌았다.
- 바인딩 값 로그 없이는 행 단위로 확정할 수 없다. 추정으로만 기록한다.

## NA2 — 곡 목록 (N=100)

조건은 기준선·N1 표 A 와 같다.
- 요청: `GET /api/music/filter?searchTerm=&sortBy=latest&page=0&maxPrice=100000&minPrice=0`
- 인증: `bidder@test.local` JWT, 페이지 크기 10
- 부하: k6 10 VU × 30s, 콜드 1회를 버리고 웜 2회차를 채택, 3회차로 교차 확인
- 재시드(N=100) 직후 앱을 기동하고, catch-up 마감(50곡)이 끝난 뒤(status0=50/status1=50) 측정했다. 측정 시각은 2026-09-26 01:0x 다.

| 항목 | 기준선 (LOB, Java 17) | **S3 이후** | 변화 |
|---|---|---|---|
| **요청당 응답 크기** | 4,098,655 B (≈4.1MB) | **6,055 B (≈5.9KB)** | **약 677분의 1** — 구조 차이(base64 커버 10건 → 커버 URL 10건) |
| 커버 전달 | `image` base64 (곡당 300KB → 약 400KB) | `coverUrl` (1시간 presigned, 곡당 약 0.5KB) | 커버 URL GET 200, 307,200B |
| 요청당 SQL (요청 스레드) | 4 | **4** | 동일 (유저 1 + 프로젝션 1 + count 1 + 좋아요 IN 1) |
| SELECT 의 미디어 바이트 열 | 없음(audio 제외, **image 포함**) | **없음 (image·audio 모두 0)** | 커버 바이트도 SELECT 에서 빠짐 |
| 웜 p(90) / p(95) | 153.7ms / 166.5ms | **51.2ms / 55.9ms** | p90 약 3.0배 단축 — 아래 해석 참고 |
| 웜 avg | 118.9ms | 38.0ms | |
| 웜 처리량 | 45.3 req/s | 71.6 req/s | **비교하지 않는다** — 아래 참고 |
| 실패율 | 0% | 0% | |

회차별 p90: 콜드 59.3ms, 웜(채택) 51.2ms, 3회차 48.5ms. 세 회차가 ±15% 안에 모인다.

### 해석
- **응답 크기와 SELECT 열은 구조 지표라 날짜 차이와 무관하게 비교할 수 있다.**
  - 기준선 4.1MB 의 대부분은 곡마다 base64 로 실린 300KB 커버였다.
  - 이제 커버는 브라우저가 S3 에서 직접 받는다. API 응답에는 URL 만 남아 약 5.9KB 가 됐다.
  - 목록 SQL 은 4개로 같다. 프로젝션 SELECT 에서 `image` 열이 빠졌다.
- **p90 약 3.0배 단축은 조건부로만 쓴다.**
  - 관측된 세션 편차(약 2배)보다 크지만, 크게 넘는 수준은 아니다.
  - 응답 크기가 677분의 1 로 줄었으니 지연이 줄어든 방향 자체는 구조적으로 설명된다.
  - 그러나 "153.7ms → 51.2ms" 같은 절대값 비교를 확정적으로 쓰려면, 기준선과 같은 세션에서 연달아 다시 재야 한다.
- **처리량은 비교하지 않는다.** k6 스크립트가 반복마다 0.1초 쉰다(`sleep(0.1)`). 그래서 10 VU 의 처리량 상한은 약 10 ÷ (0.1s + 지연) 이다. 지연 38ms 일 때 상한이 약 72 req/s 이므로, S3 이후 71.6 req/s 는 서버 한계가 아니라 스크립트 상한에 닿은 값이다.
- **재측정 경위:** 첫 측정 도중 네트워크가 불안정했다는 보고가 있어, 재시드와 앱 재기동부터 다시 쟀다. 버린 첫 실행도 응답 크기·SQL 수가 같았고 웜 p90 은 57.4ms 로 비슷했다. 목록 API 는 presigned URL 을 로컬에서 계산해서 측정 경로에 S3 네트워크 호출이 없다.
