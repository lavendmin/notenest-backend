### 해석
- **남아 있던 병목이 사라졌다.** 기준선의 웜 결제 후속 잡은 결제 대기 곡 167곡마다 `findById(Music)`를 호출했다. 이때 음원 3MB·이미지 300KB LOB 까지 매 사이클 함께 읽었다.
  이제 곡 행에는 키·메타데이터만 있어서, **같은 SQL 502개**가 1.3초 안에 끝나고 10초 주기 안에 들어온다.
  SQL 수가 같다는 것은 조회 경로나 횟수를 바꾼 것이 아니라, **한 행이 싣는 데이터**가 줄어서 빨라졌다는 뜻이다.
- **힙:** 웜 사이클 힙이 GB 단위에서 수십~수백 MB 로 내려갔다. LOB 를 엔티티로 올리지 않기 때문이다.

### 관찰 — catch-up 구간의 `UPDATE music` 수 (원인 미분리)
catch-up 구간의 SQL 을 종류별로 비교했다([원시](raw/nb1-na1-catchup-sql-histogram.txt)).
- 조회 SQL(곡 SELECT 250, 입찰 SELECT 250)은 같다.
- `UPDATE music` 은 234 → 331, `UPDATE bid` 는 500 → 498 로 달랐다.
- 최종 상태(위 불변식)는 같다. 그래서 동작이 바뀐 것이 아니라, 같은 변경을 DB 에 반영(flush)하는 횟수가 달라진 것으로 본다.
- 가능한 요인이 두 가지 있다.
  - 사이클 전체가 한 트랜잭션이다(N2 문서의 한계: 자기 호출이라 곡별 REQUIRES_NEW 가 무효). 그래서 자동 flush 시점에 따라 한 곡의 UPDATE 가 나뉘거나 다음 사이클로 넘어갈 수 있다. 실제로 기준선은 첫 결제 사이클이 522(이후 502)로 20개 많았다.
  - 기동 직후 두 잡의 실행 순서가 달랐다. 기준선은 결제 후속(대상 0)이 먼저, 이번에는 마감이 먼저 돌았다.
- 바인딩 값 로그 없이는 행 단위로 확정할 수 없다. 추정으로만 기록한다.
